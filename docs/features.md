# Feature Guide — Every Screen Explained

This guide explains what each Stratum screen does, what every term means, and why it matters to you. No jargon without explanation.

---

## Key Terms (Read This First)

Before diving into each screen, here are the terms you'll see everywhere:

**Technical Debt**
Code that works today but was written in a way that makes future changes harder, slower, and riskier. Every time a developer takes a shortcut ("I'll fix this properly later"), that's debt. Debt doesn't break things immediately — it accumulates silently until changes become painful or bugs start appearing.

**Debt Score**
A number calculated per file per commit. Higher = more debt in that file. It's built from four components:
- **Complexity** (30%) — how hard the functions are to understand and test
- **Duplication** (30%) — how much similar logic exists elsewhere in the codebase
- **Violations** (20%) — how many of your rules (from `stratum.yaml`) are broken
- **Cluster membership** (20%) — how many spreading patterns this file participates in

The weights are configurable in `stratum.yaml`.

**Cyclomatic Complexity**
A measure of how many different paths can be taken through a function. A simple function that just returns a value has complexity 1. Add an `if` statement and it becomes 2. Each `if`, `elif`, `for`, `while`, `and`, `or` adds 1. High complexity = hard to test, easy to introduce bugs, hard for other developers to understand. Stratum flags functions above your configured limit (default: 10).

**Semantic Similarity**
Two functions can look completely different on the surface but do essentially the same thing. Stratum uses an AI model (CodeBERT, trained by Microsoft on millions of lines of code) to understand what a function *does*, not just what it looks like. This is how it catches duplicate logic even when variable names are different.

**Embedding**
A mathematical fingerprint of a function's meaning, generated by the AI model. Two functions that do similar things have similar embeddings. Stratum stores an embedding for every function in your codebase and uses them to find duplicates.

**Semantic Cluster**
A group of functions spread across your codebase that do essentially the same thing. When a cluster grows, it means the same logic is being written again in more places — a spreading anti-pattern. Clusters can be benign (intentional abstractions) or harmful (copy-paste debt that should be refactored into a shared function).

**Velocity**
How fast a file's debt score is changing. Positive velocity = getting worse. Negative velocity = improving. High velocity (either direction) is worth paying attention to.

**Inflection Point**
A commit where a file's debt score changed sharply — either a sudden spike (rushed feature, large shortcut taken) or a sudden drop (refactoring sprint paid off). Stratum highlights these on the timeline so you can find what caused them.

## Page 1 — Repository Overview

**What it shows:** The current health of your repository at a glance.

- **Health Score (0–100)** — An overall score calculated from the debt scores of all files. 100 = clean, 0 = severely in debt. This number trends over time so you can see if your overall codebase health is improving or degrading.

- **Top 5 deteriorating files** — Files whose debt score is rising fastest right now. These are your highest-priority candidates for refactoring.

- **Spreading pattern count** — How many semantic clusters are actively growing. A growing cluster means the same bad pattern is being added to more files.

- **Live analysis progress** — When you trigger an analysis, a real-time progress bar shows which stage is running (ingestion, parsing, embedding, clustering, scoring). Updates via WebSocket — no page refresh needed.

**Why it matters:** First place to look when you want to understand the overall state of your codebase, or when you want to know "is this codebase getting better or worse?"

## Page 2 — PR Review Center

**What it shows:** All pull requests Stratum has reviewed, their findings, and their debt impact.

- **Health Score per PR** — A score from 0–100 for that specific PR. Calculated from the severity and count of findings.

- **Findings breakdown** — How many critical, high, medium, low severity issues were found.

- **Severity chart** — Visual distribution of issue types across all your PRs.

- **Triggered rules** — Which `stratum.yaml` rules were violated.

- **Debt impact score** — How much this PR is predicted to change your overall debt score if merged.

**What the findings look like on GitHub:**
Each finding becomes an inline comment on the exact line in the PR, showing:
- Severity badge (Critical / High / Medium)
- What the issue is
- Why it's a problem
- A suggested fix (generated by Groq AI)

**Why it matters:** Track review trends over time. If your critical finding count is rising across PRs, your team may need a security review or clearer coding standards.

## Page 3 — Debt Timeline

**What it shows:** A graph of any file's debt score across every commit in your git history.

**How to use it:**
1. Select a file from the dropdown (or search by filename)
2. The graph shows the debt score at each commit, oldest on the left to newest on the right
3. Hover over any point to see the commit message and author
4. Red markers on the timeline = inflection points (sharp changes)

**What inflection points tell you:**
- A sharp spike = something bad happened in that commit (large function added, complex logic introduced, duplicates created)
- A sharp drop = a cleanup happened (refactoring, complexity reduced, duplicates removed)

**Side-by-side comparison:**
Select two files to compare their debt timelines on the same chart. Useful for comparing how two similar files evolved differently.

**Why it matters:** "This file is a mess" is not actionable. "This file's debt score doubled in the sprint of March 12th, when we rushed the authentication rewrite" is. The debt timeline gives you the full story so you can understand root causes and prevent them from repeating.

## Page 4 — Semantic Cluster Map

**What it shows:** A bubble chart where each bubble represents one semantic cluster — a group of functions across your codebase that do similar things.

**Reading the chart:**

| Visual element | What it means |
|---|---|
| Bubble size | How many files contain functions in this cluster |
| Bubble color | Growth rate — red = growing fast (spreading anti-pattern), blue = stable, green = shrinking |
| Bubble label | A short auto-generated description of the pattern |
| Timeline slider | Drag to see how clusters evolved over your git history |

**Clicking a cluster shows:**
- Which functions belong to it (file, function name, line number)
- When each function joined the cluster
- The origin commit — the first function that established this pattern
- Growth rate over time

**Why it matters:**

Most code review tools look at a PR in isolation. Stratum looks at it in the context of your whole history. If your codebase has 8 different functions that all do essentially the same database lookup — that's Cluster #5. Now when PR #47 adds a 9th version, Stratum warns you *before you merge*. Without this view, the duplication accumulates invisibly until someone does a painful refactoring.

**Common use:** Identify the 2-3 clusters that are growing fastest and plan targeted refactoring sessions to consolidate them.

## Page 5 — Velocity Heatmap

**What it shows:** Your entire repository's file tree, with each file colored by its debt velocity (rate of change).

**Color scale:**

| Color | Meaning |
|---|---|
| Deep red | Debt growing very fast — urgent attention needed |
| Orange/yellow | Debt growing moderately |
| Grey | Stable — not changing much |
| Light green | Debt decreasing — things are improving |
| Deep green | Debt decreasing fast — active cleanup happening |

**Filters:**
- By language (Python only, JavaScript only, etc.)
- By directory subtree (just `src/api/`, just `tests/`, etc.)
- By time range (last 30 days, last sprint, last quarter)

**Why it matters:**

SonarQube tells you a file is bad today. The velocity heatmap tells you which files are getting worse *right now* — so you can intercept them before they become critical. A file that scores 30 today but has been climbing 5 points per sprint will be at 60 in three months. Catch it now.

Also useful for the opposite: confirming that a refactoring sprint actually worked. After a cleanup effort, you should see the targeted files turn green.

## Page 6 — Blame Report

**What it shows:** Every commit in your git history, ranked by how much technical debt it introduced.

**Important: this is NOT a blame tool for individuals.**
It's a tool for understanding *where* debt entered your codebase so you can prevent similar patterns. The purpose is to learn, not to criticize.

**What the ranking measures:**
- Not lines of code changed
- Not number of files touched
- The actual debt introduced — patterns originated in this commit and how far those patterns eventually spread to other files

**What each row shows:**

| Column | Meaning |
|---|---|
| Commit SHA | Clickable link to GitHub |
| Author | Who made the commit |
| Date | When it was merged |
| Debt introduced score | Numerical measure of debt added |
| Patterns originated | How many new semantic clusters started here |
| Files eventually affected | How many files later adopted patterns from this commit |

**The key insight:** A commit that changed 10 lines but originated a pattern that spread to 15 files ranks higher than a commit that changed 500 lines of clean code. The spread is what matters.

**Typical findings:**
- A rushed "temporary" implementation that became a template others copied
- A complex authentication function that was duplicated instead of abstracted
- A sprint where a library was used insecurely in 3 places simultaneously

**CSV export** — Download the full report for inclusion in sprint retrospectives or architecture reviews.

## Page 7 — Pipeline Monitor

**What it shows:** Live progress of the ingestion pipeline when you trigger an analysis, plus a list of failed tasks.

**Pipeline stages:**

| Stage | What it does |
|---|---|
| Ingestion | Walks the git history, checks file fingerprints, queues changed files |
| Parsing | Tree-sitter AST parsing — extracts functions, classes, complexity scores |
| Embedding | CodeBERT generates an embedding (AI fingerprint) for each function |
| Storage | Bulk writes to PostgreSQL + pgvector |
| Intelligence | DBSCAN clustering, debt scoring, blame mapping |

Each stage shows:
- Status (started / completed / failed / skipped)
- Items processed
- Duration

**Live updates via WebSocket** — the stage status updates in real time without page refresh.

**Failed tasks panel:**
Any stage that fails appears here with the full error message. Each failed task has two buttons:
- **Retry** — re-queues the task immediately
- **Dismiss** — removes it from the list (the stage will be re-processed on the next full analysis)

**When to check this page:**
- After clicking Analyze — to watch progress
- When an analysis seems to be stuck — to check for errors
- After a Stratum update — to verify all workers are running

## How It All Connects

Here's the full picture of how the features work together:

```
You write code
      ↓
Open a Pull Request
      ↓
Stratum reviews it instantly (PR Review Center)
  - Catches security issues, rule violations, duplicates
  - Warns: "This code will join Cluster #8, accelerating its growth by 35%"
      ↓
PR is merged
      ↓
Next analysis run ingests the new commit
  - File's debt score updated on Debt Timeline
  - Cluster #8 grows — visible on Cluster Map
  - File may appear on Velocity Heatmap if score increased fast
  - Commit ranks on Blame Report by debt introduced
      ↓
Repository Overview updates to reflect the new state
```

The power of Stratum is that these aren't separate tools — they're all views into the same underlying data. A finding on the PR Review Center connects to a pattern on the Cluster Map connects to a spike on the Debt Timeline connects to an entry on the Blame Report. You can trace any debt problem from its current state all the way back to the commit that started it.
